## Source map
- `AsePlugin.cs` plugin: cfg binds, `Entries` (what the window loads/saves), Mods-menu tick (`ModState`), cfg file watcher, `WireModules`/`ApplySettings`, `TryPatch`.
- `AnchorChainEntry.cs` entry point + `ModState` (reads the tick from usersettings.ini [LoadOrder]).
- `SettingsHub.cs` the rgreat settings hub (protocol v1), THE SAME FILE in every rgreat mod; canonical copy here. One menu entry (main menu under Mod Manager, pause menu under Options) for the settings of all installed and ticked rgreat mods.
  The mods register in a registry in `AppDomain` data (BCL types only, shared between dlls): `Register(id, title, version, order, open, active)`; `Install(harmony, gameAssembly, trace, language)` hooks `MainMenuView` ctor and `PauseMenuViewModel.Initialise(list)`.
  The first mod's hook puts the button in (main menu: a Button named `rgreatSettings`; pause: the list noted in AppDomain data `rgreat.settings.v1.pause`), the others find it. One active mod: its own title, opens its window. Several: "Alternative Mods" opens a list (Popup).
  Order: 10 Game Interface, 20 Weapons Control, 30 Damage Model, 40 Special Effects. Do not change the protocol or the logic in one copy only: edit here, copy to the others.
- `SettingsWindow.cs` table-driven window (copy of AWC's; `Add(tab, group, key, label, unit, kind, step, min, max, gameDefault)`), `Loc.cs` texts (keys `set.* tabs.* grp.* lbl.* unit.* help.*`, `menu.button`), `Release/lang/*.ini` (AWC translations reused by key; the new keys are English except ru labels).
- `Migrate.cs` first start only (no cfg file yet): reads `user/AlternativeWeaponsControl/AlternativeWeaponsControl.cfg` and `user/AdvancedDamageControl/AlternativeDamageModel.cfg` (old folder name) / `user/AlternativeDamageControl/AlternativeDamageModel.cfg` (new name, wins) and sets the same [Section]/Key values.
- `Flash.cs` flashes, fire light, fire flicker; `EffectsGuns.cs` gun effect hooks; `FireSmoke.cs`; `HideUnseen.cs`; `BubblesOff.cs`; `R.cs` reflection helpers.
- `SettingsHub.Install` does not patch the menu classes at plugin start (their static constructors register Noesis properties too early: native crash of the Release build); it waits for the end of the load screen (`LoadScreen.ExecuteLoadScreen` iterator finished) and then patches, adding the button to an already built main menu.
- Smoke colour step at the horizon (brown over the sea, grey over the sky; also in the base game): the game's colour grading `AmplifyColorEffect` has a depth mask (`CameraManager.setAmplicyColorValues`, every frame: UseDepthMask = !overcast); transparent smoke has no depth, so its grading follows the depth behind it (sea near / sky = far plane). Found with the debug switches (tab Debug: camera effects off one by one; SSMS/Sun shafts, the shader's `_FogFadeFactor`, the sky meshes - queues 2100..2999 - and our smoke fade were ruled out). Fix `ColourGradingNoDepthMask` (default on): postfix sets UseDepthMask = false. Note: switching the component off and on also removed the step (its depth mask seems broken after a re-enable) - not used, it is an accident. The debug dump 'sky and late renderers' lists the sky meshes, late renderers and the camera's components.
- The settings window keeps the scroll offset across Apply (`_keepScroll`, put back for a few frames while the rebuilt window lays out).
- `SmokeDensityFactor`: done in `Prolong` (state per effect from the game's base values): `emission.rateOverTimeMultiplier` x factor on every system of the effect (flames included; bursts are not touched), `maxParticles` raised to fit; applies to burning ships at once.
- `FireSmoke.Prolong` (postfix of `CreateFireEffect`, and once a second from `Tick` for every fire effect of the ship) + `AseFireStretch` (src/FireStretch.cs): two stages of a fire particle's life. The fire system (root `shipfire_*`, sprites carry fire then smoke) stays EXACTLY as the game made it: start lifetime and every over-lifetime curve untouched, so the first `SmokeFireShare` (30%) of each particle's life is the game's (size, alpha, frames, velocity). A particle job (`IJobParticleSystem`, scheduled from `OnParticleUpdateJobScheduled` on the system's GameObject, i.e. by the engine after its own update - no polling) multiplies `inverseStartLifetimes` by 1/`SmokeLifetimeFactor` once, when `aliveTimePercent` passes the share: the lived share stays, so all curves continue from their value k times slower (no jump, the particle does not brake: each velocity value is held k times longer). A particle is stretched once: afterwards its 1/lifetime is below a cut between the game's range of 1/lifetime (from `main.startLifetime`) and the stretched range (geometric middle of the gap; with no gap, k <= max/min life, a short-lived particle may be stretched a few times until below). A custom data mark was tried and FAILED: the custom data module writes its curve into the stream every update, the mark was lost, particles were stretched every frame, froze at 30% and never died. Spread (`SmokeSpreadGrowth` 50%, `SmokeSpreadFade` 100%): slowed particles fly k times longer, so the column's sprites end far apart; over the slowed part of the life (u = share..1 - only slowed particles are there) the system's size curve is x M and the colourOverLifetime alpha x M^-fade, M = 1 + grow (r - 1), r = (share + (1-share) x k) / (share + (1-share) x), x = 0..1 through that part; the first part keeps the game's curves (keys copied), base curves kept once in the component, rebuilt only on a setting change. Frame time: a slowed particle is removed (aliveTimePercent = 100 in the job) once its opacity (game alpha x M^-fade) stays below 2% to the end of its life (computed per system on a setting change, traced as 'removed at N%'): the grown late sprites are big, nearly transparent and still drawn with the two-pass fire shader (fill rate). SmokeDensityFactor 2 doubles all of it; with SmokeSpreadGrowth the grown sprites already close the gaps, so density 1 may be enough. `maxParticles` x (share + (1-share)k) x density, rate x `SmokeDensityFactor`. Smoke-only systems (material name has "smoke") get start lifetime x k. HISTORY (do not repeat): re-timing the curves instead (frame + size warp) never matched the game - the size and the alpha of the threshold shader (`Particles/Particle_Multi_Pass`: `_Threshold/_Min/_Multiplier`) both set the visible size, re-timing size alone was off (once 2x: `sizeOverLifetime.size` and `.x` are one curve and were warped twice). The debug dump of a new fire effect (made before our changes) lists main/shape/modules/startSize/sizeOverLifetime/sheet/subEmitters of every system. Unverified in game.
- `HideUnseen.cs`: the source of "seen" is the game's visual sensors: postfix of `SensorSystemVisual.runVisualScan` (own side only) stores the sensor's `_detectedObjects` (rebuilt in one go per scan, kept until the next); an object is seen when any list holds it. `Vehicle.IsObservedByVisual`/`DetectingSensors` are NOT used (reset at the start of every `UpdateFromECS`, Visual bit absent for a moment once per game second - blinked). Contacts become known via postfix of `Vehicle.UpdateFromECS` (record with `ReportingSide` = player). The camera is not sent to a hidden contact (prefix of `RenderPosition.switchToObject`) and lets go of one that becomes hidden (`deselectObjectAndDetachCamera`); the blocked/released target is remembered (`_pending`, cleared by any other switch) and the camera is sent back with `switchToObject` as soon as it is shown again. Wake effects are not cut off but stopped at the source so what exists fades by itself (all parented under the unit's "Particles" child by the game loaders): particle systems (bow wave, prop wash, cavitation, funnel smoke) emission off; `Ceto.AddFoamTrail.duration = 0` (no new foam, old foam ages out); `Ceto.AddWaveOverlay` (Kelvin patch, single overlay) disabled. Restored on show. The towed/dipping sonar cable (a line renderer of its own object, not part of the unit model) and the towed body are taken from `ObjectBase._obp._towedSystems` and hidden with it. Hides with `Renderer.forceRenderingOff`; no timers. Life raft lights blink: `_Interval=2` in `vessels/all_life_rafts/red_light*.ini` (value is a guess, tune in-game).

## Save / load rules (checked against the decompiled code)
- No timer outside objects of the scene; game-time deadlines (`GameTime.missionElapsedTime`, not `Time.time`: time compression caps `Time.timeScale`).
- Bubbles: the save keeps only `IsSinking`, not `_sinkTime`, and the load does not call `Sink()` or respawn the bubbles. So `BubblesOff` patches `Compartments.Sink` (postfix)
  and adds a `BubblesTimer` component to the ship's transform where the bubbles are children; it stops them after `BubblesStopMinutes` of game time and destroys itself. A ship loaded as sinking has no bubbles
  from the game, nothing to stop. The timer dies with the scene.
- No cached scene objects in statics: the sky singleton is looked up per call (guarded by `InstanceExists(false)`); the donor AudioSources and clip loudness table are bound to the `EffectsManager` instance and collected again when it is gone.
- Smoke: `FireSmoke.Tick` runs once a second per ship from the game's own `Compartments.OnFixedUpdate` prefix; per-ship state is in a `ConditionalWeakTable`.

## Data and switches
Gun hit effects (`HitEffects.cs`, [Effects] GunHitEffects, [GunHits] Class1..10): no data file and no `[Particles]` in any ini. A postfix on the `AmmunitionParameters(string, int, WeaponSystem)` constructor notes every projectile
(weak reference, state in a `ConditionalWeakTable`), keeps the game's own five hit `Effect` objects (HitDefault/Air/Ship/Ground Explosion, HitWaterSplash; taken after the game loaded the ini, so other mods' layers are in them) and, with the switch on,
puts the values of the shell's class into them in place (`_effectClassName`, `_singleEffect` = null, `_isAvailable`, `_isIgnored`, `_scale`). The class (tier 1..10) comes from the mass (`_massInKg`, kg): the first class whose upper mass (settings Class<n>UpToKg, defaults 0.4/5/8/16/28/42/110/400/1200) is not below it. The calibre is not used (checked: the game does not read the ini key Caliber, and one mass limit set fits the game's and the WW2 mod's shells differently - the older shells are lighter for the calibre). Not touched: not Projectile, no mass, star shells (the kept effects are star shell ones).
Per tier: ship = the mod's own collection ASE_Ship_1..9 (variants of the game's prefabs; `spawnEffect` picks ONE random variant of a class, so a class is a set of variants, not a combination), air / water / ground = the game's classes of effects.ini
(the table is in the code: Air, Water, Ground, ShipVariants; null in Ground = the game's value stays) and the scale of each (`Effect._scale` -> `localScale` of the spawned effect; settings Class<n>Ship/Air/Water/Ground, default table in `Scales`).
The classes ASE_Ship_n are put into the `EffectsManager` by a postfix on `EffectsLoader.load` (the manager is a mission singleton and is built again for each mission; `addEffectClass` ignores a name that exists) and once at start.
A change of a setting / the switch / the Mods tick (`ApplySettings` -> `HitEffects.Sync`) applies the values to every noted object again. A loaded game builds new AmmunitionParameters: the constructor hook handles them.
Known risk to check in the game: the effects come from `PoolManager`, and the game sets `localScale` only when `_scale` is not zero, so a scaled instance may come back from the pool for an effect with a zero scale; the mod always writes an explicit scale into the slots it manages.
Life raft lights (`RaftLights.cs`, [Effects] LifeRaftLights): the three `ase_all_life_raft*.patch.ini` in `vessels.fix` + `vessels/all_life_rafts/` are an ordinary `#!extend` layer of the mod (always loaded while the mod is ticked).
The switch shows / hides the parts drawn with the shader `Nils/Effects/MeshLights` on the rafts (`ObjectsManager._listOfAllRafts`, and a postfix of `AddObjectToItsTaskforce` for rafts that appear, also after a load).
The extend rules of the game, for reference (IniHandler): extend files of a target are read before the target, the FIRST value of a key wins, an empty `Key=` is a value.

- Settings window: groups listed in `SettingsWindow.SubGroups` (the five engine groups of Funnel Smoke) are shown one at a time as sub-tabs inside their tab (`_curSub`, `SubTabs`); fields of other groups of the tab stay above.

- Funnel smoke thickness: the funnel smoke material is `Legacy Shaders/Particles/Alpha Blended` with `_TintColor` alpha 0.02 (final alpha = 2 x tint x particle colour), and the particle's own alpha is already 1, so scaling the colours changes nothing. Thickness therefore multiplies `_TintColor` alpha through a per-renderer MaterialPropertyBlock (the material is shared by all ships).
- Funnel smoke lightness and thickness go through the material's `_TintColor` (per-renderer MaterialPropertyBlock; shader Legacy Alpha Blended: 2 x tint x vertex colour x texture). Lightness (`{Group}LightIdle/LightFull`, %, replaced the old `Bright*` multipliers - a uniform multiplier kept the brownish hue: black -> orange, never white): the smoke's average colour = texture average (alpha-weighted, read once per texture via Graphics.Blit to a 32x32 linear RenderTexture + ReadPixels) x start colour x colorOverLifetime average (alpha-weighted), in the project's colour space; tint per channel = wanted grey / (2 x that), capped at 16, converted back to gamma in linear space. Trace: 'funnel smoke: texture ... average colour', '... smoke colour ..., the game's result ...'. Thickness x tint alpha (_TintColor alpha is only 0.02). The tint is fixed per ship (white, alpha x the group's higher thickness); lightness and thickness by the load go into the START colour of the particles (`main.startColor` x fraction), so a change of the engine mode affects only new particles. Unverified in game.

- Fire stage change (`SmokeKeepOnStop`): `Compartments.FireEffect.Deactivate` calls `ParticleSystem.Stop()` = StopEmittingAndClear, which erased the live smoke when a point switched small/moderate/severe or went under water. A transpiler on Deactivate replaces that call with `FireSmoke.StopFire` = `Stop(true, StopEmitting)` (runtime switch). Unverified in game.
- The random start moment (`Scatter`, pre-run with `Simulate`) was REMOVED; the random seed stays (`FireSmoke.RandomSeed`, every new effect, no pre-run): it gave instant smoke columns on hits/F10 and was glitchy. Do not bring it back.
- Smoke and clouds (`SmokeAfterClouds`, fires and funnels; the cfg key kept its old name): clouds are one MeshRenderer per sky cell (TurboClouds.buildMesh: km-wide bounds, many billboard quads, queue 3000 like the smoke), Unity sorts a whole cell against a column by the bounds centre - the game's bug. The first fix (smoke material queue = clouds + 1, smoke always after the clouds) was wrong from above the clouds and for far ships: REMOVED, materials keep the game's queue. Now in PreCull every column (fire effect or funnel smoke, `Track`) gets sortingOrder = game's + 1000 x side - rank: side = -1 (behind the clouds) when more of the cloud layer (CloudsManager.getCloudsMinHeight..MaxHeight, looked up lazily) lies on the ray camera -> column (bounds centre) before the column than after it over the same length, else +1; no clouds -> 0. Whole columns vs whole cells, not per pixel. With SmokeAfterClouds off the ranks of SmokeSortFix are compared with the clouds' order 0 too (sortingOrder beats distance in one queue). Unverified in game.
- Smoke order (`SmokeSortFix`): columns are ranked by the exact distance from the camera to their emitter points (no rounding; equal ones by creation order), rank i - N/2 goes into `sortingOrder` (nearer = higher), set in Camera.onPreCull / beginCameraRendering. History: a sortingFudge compensation by the bounds' centre flickered (noisy bounds); a tie window made the order follow the creation order (bow to stern).

## Settings hub under R.A.T.S. Keel
- Keel starts the mods after `LoadScreen.ExecuteLoadScreen` is over, so the `LoadScreenPostfix` never fires. `SettingsHub.Install` first checks `LoadScreenIsDone` (`Singleton<LoadScreen>.InstanceExists` -> `Instance` -> `LoadText == "Done"`) and, if so, installs the menu entries at once and gives the already built main menu its button. Under Anchor Chain the old path (wait for the end of the coroutine) is unchanged. The canonical copy of `SettingsHub.cs` is here; ADM, AWC and AGI take it unchanged.
- `Register` ends with `RefreshLabels()`: a mod that registers later than the first one (early start under Keel, so far AGI) refreshes the text of the main menu button and the pause menu buttons that are already there ("Alternative Mods" for two or more active mods, the mod's name for one). Does nothing until the hub is installed (`_game == null`). Copy of the hub is the same in ADM, AWC and AGI.
